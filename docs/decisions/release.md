# Decisions — docs & release engineer

- **Service worker generated by an own Vite plugin (`scripts/sw-plugin.ts`) instead of vite-plugin-pwa or `scripts/build-sw.mjs`.** No new dependency; running inside `vite build` (`closeBundle`, post) means every build — `npm run build`, the E2E `webServer` build, `--outDir` variants — gets a matching worker with no extra step. The static `public/sw.js` placeholder was deleted so it can never overwrite the generated one. (ARCHITECTURE.md §3 still names `scripts/build-sw.mjs`; it should say `scripts/sw-plugin.ts`.)
- **Precache list = every file in the output folder after the build, minus `sw.js` and `*.map`.** Walking the folder (rather than Rollup's bundle) includes the copied `public/` files (manifest, icons) with no allow-list to keep in sync.
- **Cache version = first 12 hex chars of SHA-256 over file names and contents.** Any changed byte produces a new `sw.js`, which is what makes the browser install an update; unchanged builds keep the same worker.
- **All worker URLs are resolved relative to the worker's own URL.** Works under `/<repo>/` on GitHub Pages and from any folder, matching Vite `base: './'`.
- **Navigations are served cache-first from the cached `index.html` (app shell).** The cached shell always references the hashed files in the same cache, so a page is never a mix of two versions; a network-first shell would break offline start on flaky tablet Wi-Fi.
- **No `skipWaiting()` and no update message handler (fix round: the unused `'skipWaiting'` handler was removed).** A new version installs in the background and applies only after every app window/tab is closed and the app is reopened; the README says exactly that. Taking over a running game could leave the page requesting hashed files the new cache no longer has. `clients.claim()` on activate makes the very first visit controlled, so it is offline-ready without a reload.
- **Non-precached or cross-origin requests are not intercepted.** The game has no runtime network data; letting them go to the network keeps the worker simple and avoids caching anything unbounded.
- **Manifest gains `id: "./"`, `lang`, `dir` and `categories`.** A stable `id` keeps the installed app's identity if `start_url` ever changes; the rest are metadata stores and launchers read. Other fields were already right.
- **`static-check` also enforces the 6 MB download budget** (sum of all files in the build, worker included, 1 MB = 10⁶ bytes) and prints the five largest files, so the budget is checked every time the static check runs.
- **`static-check` is strict by default (requires `[data-testid="btn-mode-freeKick"]`) with an `--allow-stub-ui` escape for early phases.** The Phase 3 run must prove the real title screen appears; the flag only exists so the script could be verified before the UI landed.
- **Offline E2E runs twice: at the `vite preview` root and under `/LT26/` served by a tiny Node static server inside the spec** (from `PW_OUT`, the folder the webServer just built), so it needs no Python and no second webServer entry. It requires the title button online (count > 0) and offline, and `scene.getStats().drawCalls > 0` offline, so it cannot pass against an empty page.
- **Offline E2E asserts `response.fromServiceWorker()` only on Chromium.** Playwright reports that flag only for Chromium; on WebKit/Firefox a clean offline boot with zero failed requests is the proof.
- **`vite.config.ts` imports the plugin as `./scripts/sw-plugin.js`.** Vite warns that extensionless imports are unsupported by its future native config loader; `.ts` would need `allowImportingTsExtensions` in tsconfig, which I may not edit. TypeScript's Bundler resolution maps `.js` to the `.ts` source.
- **Pages workflow uses separate build and deploy jobs, Node 22, `actions/configure-pages@v5`, `upload-pages-artifact@v3`, `deploy-pages@v4`, concurrency group `pages` without cancel-in-progress.** This is GitHub's reference layout; not cancelling avoids half-finished deployments. It builds with `npm run build` (type-check included) and does not rerun tests — CI does that on the same push.
- **CHANGELOG lives at the repository root** (my brief), not `docs/CHANGELOG.md` as in the brief's §5 tree; the root is where people and tooling look for it.
- **README states iPadOS/iOS 16+ as the Safari floor.** It is the oldest Safari with the WebGL 2 and service-worker behaviour the game relies on that is still commonly in use; the brief only says "Safari on iPad/iPhone".
- **CI split (fix round): a fast `check` job (lint, unit, build, `static-check`, 20 min) and an `e2e` matrix with one job per Playwright project (60 min each, `fail-fast: false`), each installing only its browser.** Parallel jobs keep wall time near the slowest project; `fail-fast: false` shows every browser's result. Superseded runs on the same ref are cancelled.
- **WebKit, iPad and Firefox jobs pass `--grep-invert visual\.spec\.ts`.** The visual tests are not tagged `@visual`, but Playwright's grep matches against the title path including the file name, so this excludes exactly visual.spec.ts (verified with `--list`). Baselines exist only for chromium and tablet-android on Linux.
- **Pages workflow runs `npm run lint` and `npm test` before the build** so a red tree never deploys, without repeating the slow E2E suite (CI covers that on the same push).
