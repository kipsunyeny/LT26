# Decisions log

Every choice made instead of asking the owner. Newest at the bottom of each phase. Format: **D-nn — decision.** Why.

## Phase 0 (orchestrator)

- **D-01 — Build in a persistent cloud workspace and sync the repository into `DevEnv/LT26` on the owner's Mac.** The Mac-side shell has a 3-minute call limit and cannot delete files; a long multi-agent build with Playwright needs a persistent machine. The owner's folder receives the full repo (including `.git`) at checkpoints and at the end.
- **D-02 — Toolchain pinned:** three 0.186.0, TypeScript 5.9.3 (TS 7 is too new for typescript-eslint 8.70), Vite 8.3.0, Vitest 5.0.1, Playwright 1.56.1 (matches the preinstalled Chromium 141 build), ESLint 10 + typescript-eslint 8.70, Prettier 3.9.8. Exact versions (`-E`) so `npm ci` is reproducible.
- **D-03 — Vite `base: './'`.** Relative asset URLs work on the GitHub Pages sub-path and from any plain static folder (`python -m http.server` in `dist/`), with no repo-name coupling.
- **D-04 — World frame:** goal line z = 0, pitch z > 0, kicker looks down −z, +x = kicker's right, y up. Matches Three.js camera defaults so no axis flips between physics and render.
- **D-05 — Spin sign convention:** `sideSpin > 0` ⇒ curves right (+x); `topSpin > 0` ⇒ dips. The UI translates to "inside/outside of the foot" labels depending on footedness; physics never sees footedness.
- **D-06 — `KickIntent.power` ∈ [0,1] maps linearly to 40–115 km/h;** the swipe scheme applies its ease-in curve before producing `power`, so the dial and swipe share one mapping.
- **D-07 — Timing penalty shape:** outside ±80 ms the power multiplier falls linearly to 0.75 and extra scatter rises linearly to σ = 3° at ±400 ms, clamped beyond. The brief gives the end points but not the width; 400 ms is roughly one running stride.
- **D-08 — Intent timestamps use the sim clock** (`state.time·1000` ms), not wall-clock, so scripted E2E and unit tests are deterministic and pausing/throttled tabs do not create phantom timing errors.
- **D-09 — Brand images are pre-resized into `assets/brand/*.webp` and committed** (`npm run assets`, uses sharp as a dev dependency). The build never needs sharp; total image weight ≈ 230 KB. PWA icons (any + maskable on navy + apple-touch) are generated from the logo the same way.
- **D-10 — `npm run lint` = ESLint + Prettier check + `scripts/no-todo.mjs`,** which fails on TO-DO/FIX-ME markers and on skipped/only tests, enforcing the "no TODOs, no disabled tests" rule mechanically.
- **D-11 — E2E runs against the production build** (`vite preview`), not the dev server, so the tested artefact is the shipped one.
- **D-12 — WebGL in headless Chromium uses SwiftShader** (`--use-angle=swiftshader --enable-unsafe-swiftshader`).
- **D-13 — `main.ts` exposes `window.__lt26` (DebugHook) in production too.** It is read-only plumbing (sim, scene, recent intents/events) that the E2E suite needs against the production build; it exposes nothing sensitive.
- **D-14 — Separate `src/contracts.ts` holds all shared interfaces** (the brief's `BallState`, `KickIntent`, `SimEvent`, `SceneApi`, `InputScheme`, `Recording` plus supporting types). Agents import types from there only.
- **D-15 — Audio is owned by the rendering engineer** (presentation layer) and is synthesised with WebAudio at runtime (0 KB of files), which trivially meets the ≤ 300 KB audio budget and avoids licensing questions.
- **D-16 — Settings persistence (`src/data/settings.ts`) is orchestrator-owned** because both sim and UI read it. Default scheme: swipe on touch devices, dial on mouse-only devices (brief: swipe is default on touch).

## Phase 2 (orchestrator)

- **D-17 — Contract v2:** added `Sim.cancelRunUp()` (a tap or cancelled pointer after the run-up started must not leave the sim stuck in `runUp`) and `SimulateOptions.ground` (the physics engineer's free-flight switch, used only by the §4 acceptance rows and the aim solver). `ShotSummary.missDistanceM`/`timeToGoalS` semantics made precise for saved/blocked shots.
- **D-18 — §4 acceptance rows are free-flight (ground off).** The brief's launch angles take several rows below y = 0 before the goal line (e.g. 6° from 25 m crosses 2.15 m below ground); with the ground on every row bounces first. The table can only describe free flight, so the tests measure that. Reviewed and accepted by the independent reviewer.
- **D-19 — §4 wall-clearance row is a spec contradiction, resolved with back spin 10 rev/s.** A 15°, 95 km/h ball is 1.93 m high at 9.15 m even in vacuum, so no spinless ball can pass ≥ 2.3 m. The test keeps every stated number and adds the one free parameter (back spin 10 rev/s, the brief's largest spin magnitude); a companion test proves the spinless case cannot pass. The reviewer noted the game's dip control only reaches −6 rev/s; in play a wall is cleared with ≈17–18° elevation. Recorded here for the owner rather than weakening the assertion.
- **D-20 — Knuckle force kept at the brief's bound (±0.25 m/s², 60 Hz).** With that bound and the "no-spin deviation < 0.05 m" row, spinless power shots wander only millimetres to a few centimetres. That is what the brief's numbers imply; raising it would break a §4 row, so it stays.
- **D-21 — Strikes are only accepted in the phase that allows them:** free kick while aiming; penalty only during the run-up; long shot only after the push. Skipping the run-up would otherwise be strictly better than timing it.
- **D-22 — Timing penalties apply to ball speed** (not the 0–1 power value), so "drops to 75 %" means 75 % of the speed. Long shot: ×0.90 just outside ±80 ms down to ×0.75 at 400 ms (brief: 10–25 %).
- **D-23 — Long-shot balance (QA D-3):** the short push (2–5 m) put the closing defender on top of the ball and the mode became unwinnable. The defender now starts 12 m ahead, reacts 0.3 s after the push and holds ≥ 3.5 m; the long-shot keeper only side-steps while the ball is > 0.55 s away. Well-placed corner shots now score about 2 in 3; central shots are mostly saved or blocked.
- **D-24 — Swipe finger speed uses 96 CSS px/in for mouse and 150 CSS px/in for coarse pointers** (tablets measure 132–160), so the brief's 0.3–2.5 m/s range maps to the finger's real speed on the tablet.
- **D-25 — CI is split into a fast check job and one E2E job per Playwright project;** visual baselines are Linux-Chromium only, so WebKit/Firefox jobs exclude `visual.spec.ts`. Pages deploy runs lint and unit tests before building.
- **D-26 — Service worker never calls `skipWaiting`:** an update applies after all app windows are closed and reopened. Predictable, and a half-updated game can't mix old and new chunks.

## Agent decision logs (merged verbatim)

### physics

- **Integrator: classical RK4 on (p, v) at 240 Hz, with ω decayed exactly (ω₀e^(−t/τ)) inside the step.** §4 allows semi-implicit Euler or RK4; semi-implicit Euler has ≈2 cm error after 1 s, while RK4 is exact for constant acceleration. The energy row measures 3.2e-13 m.
- **Contacts are resolved after the flight step (colliders in list order, swept, then the ground).** This keeps the flight integrator smooth and puts one contact model in one place.
- **Acceptance rows are measured in free flight (`ground: false`).** In free flight, the brief's launches cross below y = 0 before the line: 6° from 25 m crosses at y ≈ −2.15 m, and the penalty at −0.33 m. So the table can only describe free flight, and with the ground on every row bounces first. I extended the API in a backward-compatible way: `simulate(l, env, opts?: PhysicsSimulateOptions)` with `ground?: boolean` (default true), and `stepBall(..., colliders?, ground = true)`. The game never sets it. Proposed contract change: add `ground?: boolean` to `SimulateOptions`.
- **Wall-clearance row contradicts §4 without spin, so it is resolved by choosing the unstated spin: back spin 10 rev/s.** At 15° and 95 km/h, the vacuum parabola is only 1.93 m high at 9.15 m, and drag only lowers it (modelled: 1.89 m). No spinless model can reach 2.3 m. I kept the brief's distance, speed, angle and bound, and supplied the one parameter the row leaves open. The kick is the "lofted with back spin" bottom-of-ball strike of §3, at the brief's largest spin magnitude (10 rev/s). It measures 2.302 m, a thin 1.7 mm margin, and the test is deterministic. A second test asserts the impossibility (vacuum < 2.3 m). Consequence for sim/UI: the dial's back-spin range (−6 rev/s) cannot clear a 2.3 m obstacle at 15°. Clearing a jumping wall needs about 17–18° of elevation.
- **Knuckle force: 60 Hz value noise (quintic fade), two independent channels (x, y), magnitude clamped to 0.25 m/s², scaled by ρ/1.20, component along v removed.** It is active only when speed > 20 m/s and |ω| < 2π rad/s (1 rev/s, my reading of "near-zero spin"). Scaling by density makes it vanish in vacuum and makes it slightly weaker in Nairobi, as an aerodynamic force should. Because it is zero-mean at 60 Hz, its double integral is small: the 25 m spinless free kick wanders 7 mm (< 0.05 m) and time/speed stay within 1 % of the spin case. Both parts of that row hold with knuckle on. There was no contradiction, but the result is that "wander" is mm-scale under the brief's own bound.
- **Ball moment of inertia I = (2/3)·m·r² (thin shell).** A football is a pressurised shell. This factor sets the slide→roll coupling: a skidding ball settles at 0.6·v₀.
- **Ground: bounce if approaching faster than 0.35 m/s, else resting contact.** On a bounce, the Coulomb friction impulse is limited to μ(1+e)|v_y|. In resting contact it is limited to μ·|Δv_y| of the step (the normal impulse), so rolling ↔ sliding uses the same formula.
- **Rolling resistance: constant deceleration 0.06·g.** It is tuned (this is the only tuned number) so that a ball rolling at 4 m/s at sea level stops in 9.9 m, including air drag. The brief asks for "~10 m".
- **Rest: a ball on the ground slower than 0.05 m/s is stopped. `simulate` stops after 0.25 s below that speed.**
- **Posts/bar/players: capsule/sphere contact reflects the velocity relative to the collider's `velocity` field, with the collider's restitution; tangential velocity and spin are unchanged.** The brief specifies restitution only, and a frictionless rim contact is the simplest honest model. Separating contacts are ignored. The step is swept in sub-samples of at most half the combined radius, so fast balls cannot tunnel.
- **Net = absorb box (x ±3.78, y 0…2.56, z −2…0), open at the front.** Inside the bag: linear damping 1.5/s. The side, roof and back netting return 10 % of normal speed and keep 30 % of tangential speed and spin. From outside, the same faces (grown by r) stop the ball, so a side-netting miss stays outside. A 'net' ContactEvent fires when the normal approach speed is > 0.5 m/s.
- **ContactEvent for resting/slow contacts (< 0.5 m/s normal speed, or ground settling) is suppressed.** Otherwise a resting ball would emit an event every step.
- **Solver: free flight, Newton + Broyden on (azimuth, elevation) from the vacuum low-trajectory guess, 5 mm tolerance; returns null if not converged or if target.y < r.** Free flight keeps the residual smooth: trial steps that would bounce made the ground-on residual flat. A direct flight to a centre height ≥ r cannot touch the ground before the line, so the solved launch is also correct with the ground on (the tests verify it that way).
- **`collideGround(s, dt, g)` and `collideCollider(prev, s, collider, index, dt)` signatures.** ARCHITECTURE §3 leaves them as `(...)`. Both return `{ state, contact | null }`.

### render

- **Talilei's drawn ball is erased at load time.** The brand art has a ball between his feet; a canvas `destination-out` pass (traced leg edge + circle, `processTalileiImage`) removes it so only the real 3D ball shows. The source asset is untouched.
- **Talilei is hidden under the title camera, and so are trails/ghost/aim.** The title UI shows its own 2D Talilei over a dimmed backdrop; a second 3D one would duplicate him.
- **Kick camera: 4.5 m behind, 2.3 m high, shifted 0.5 m away from the taker, pitch chosen so the resting ball sits at NDC y = −0.55.** This puts Talilei (placed left of the ball by the sim) in the lower-left and the crossbar in the top third at every distance from 11 to 35 m. The taker side is inferred from `world.taker.p`, so left-footers mirror automatically.
- **Kick camera anchor (`KickAnchorTracker`, pure, unit-tested):**
  - A ball resting on the ground (< 1 m/s, y < 0.25) with the taker within 4 m is the kick spot. The camera snaps to it when a snap was requested or the spot jumped more than 2 m (Next kick, a preset change); otherwise it glides (τ = 0.25 s).
  - A ball rolling on the ground below 10 m/s with the taker within 8 m (the long-shot push) is followed exactly, so it keeps its size for the strike.
  - A ball above 10 m/s has been struck. The anchor freezes until the ball rests beside the taker again, so the camera never follows a shot or snaps onto a ball in the net after Replay → Back.
  - With no known spot, the anchor is derived from the taker's position.
- **Trail tubes thin inside 3 m of the camera and drop segments within 1.5 m,** so a trail can never fill the screen. A growing trail (same or prefix-equal array) is appended in place, an identical one is a no-op, and the eye-based rebuild only happens when the camera move can affect thinning.
- **Short screens: the resting ball's NDC y is `clamp(280/H − 1, −0.55, −0.4)`.** Framing is unchanged for heights ≥ 622 px (1280×800); on short screens the ball keeps about 140 px above the bottom HUD.
- **Audio `unlock()` is idempotent.** It creates the context once, and every call resumes a context that isn't running (iOS 'interrupted'/'suspended'). A `visibilitychange` → visible listener does the same.
- **`setTrail(points)` with `ghost` undefined leaves the ghost unchanged; `null` clears it.** The UI can then update the live trail every frame without passing the ghost again.
- **Ball spin integrates over the snapshot clock (`world.t` delta) when it advances, else over render dt.** Replays played at 0.35× therefore spin at 0.35× too.
- **`getStats().frameMs` is an EMA of the wall-clock interval between `render()` calls** (the frame period), not CPU time.
- **`createScene` returns `SceneDebugApi` (a `SceneApi` plus `ready: Promise` and `setDynamicVisible`).** The harness uses these to wait for the sprite and to measure the static scene on its own. It is still assignable to `SceneApi`.
- **The far half of the pitch and the far goal are built, merged into the same meshes (no extra draw calls),** so replay/title cameras never see an empty end.
- **Night stadium with a single rounded "bowl" of stands (one crowd mesh, one 2048×1024 canvas texture), no shadow maps.** Blob shadows are one InstancedMesh. Lambert/Basic materials only.
- **Replay orbit sweeps ±18° with a 30 s period (< 4°/s), high side view on the side opposite the ball's start, distance fitted to the path's bounding sphere.**
- **Audio `play('crowd', i)`: i < 0.5 (default 0.3) keeps the murmur loop running; i ≥ 0.5 also adds a cheer swell.** The contract has one `crowd` name for both. A murmur requested before `unlock()` starts once the context resumes.
- **The AudioContext is created in `unlock()`, not in `createAudio()`,** so Chrome never warns about an autoplay-blocked context.
- **No `tests/e2e/render.spec.ts`.** The E2E suite runs against the production build, which doesn't include the harness; the harness is checked with `tests/harness/shoot.mjs` instead, as briefed.
- **Screen queries never lag a camera change (`CameraRig`).** After a frame, `worldToScreen`/`screenToGoalPlane`/`ballScreenRadius` use exactly the camera that frame was drawn with. Between `setMode`/`setCamera` and the next `render()` (the first play frame can take seconds under SwiftShader), they use the pose the next frame will use: title/replay poses immediately, and for the kick camera a provisional anchor at the queried resting ball (y 0.05–0.25, z > 5), else the kept kick spot. Before, the title projection leaked into the HUD's ball hit zone.

### sim

- **Preset spots.** `fk-centre` (0, 22), `fk-left-d`/`fk-right-d` (∓6, 18.5) just outside the box at the edges of the D, `fk-wide-left`/`fk-wide-right` (∓15, 18.5); `pk-spot` (0, 11); `ls-centre` (0, 26), `ls-left`/`ls-right` (∓9, 25). All free kicks are 16–35 m from the goal centre and outside the penalty area.
- **Free placement snaps to whole metres and stays outside the penalty area.** The key `fk-x{X}-z{Z}` then names exactly one ball position. A request inside the box moves to the nearest valid point, because a direct free kick cannot be taken inside it. `setSpot('fk-x3-z25')` is accepted too.
- **The wall covers the post on the ball's side; a central ball (|x| < 0.5) is walled on the left post.** A right-footer's natural inside-foot bend goes right to left. The outside man stands with his centre on the ball→post-centre line (x = ±3.72). The line is perpendicular to that direction at 9.15 m, spaced 0.5 m and extending towards the goal centre.
- **Wall count comes from the angle the goal subtends:** ≥ 16° → 5, ≥ 12.5° → 4, else 3. That gives 5 for close central kicks, 4 for wide or 30 m kicks and 3 from 35 m.
- **Wall jump is ballistic:** v0 = √(2g·0.4), 0.15 s after the strike, airborne about 0.57 s. The capsules carry the jump velocity for collisions.
- **Free-kick keeper stands 0.8 m from the goal-angle bisector towards the far post, 0.5 m off the line.** He reacts 0.10 s later than normal, because the wall screens his view.
- **Keeper model:** the hands' midpoint moves inside a superellipse envelope |dx/2.9|⁴ + |(y−1)/1.2|⁴ ≤ 1 around his set position, which gives 2.9 m either side and a 2.2 m top. Motion is acceleration-limited: lateral 24 m/s² up to 7.5 m/s, vertical 30 m/s² up to 5 m/s, with quick braking but a full push-off to reverse. A full-stretch dive takes about 0.5 s and a 0.5 m reach about 0.2 s. The feet step up to 0.9 m. The body capsule runs from the hip towards the hands (radius 0.22, 1.45 m + radius). The hands are two 0.12 m spheres. After the reaction he re-predicts the ball every 0.05 s by stepping physics `stepBall` from the live ball state, with no noise and no colliders. That is a prediction, not a gameplay trajectory.
- **Keeper side-steps (≤ 3 m/s) only when the predicted ball is beyond his reach at that height, and only until 0.55 s before it arrives.** From then on it is the dive alone. A slow lofted shot can still be reached, a penalty (about 0.4 s) cannot use side-steps, and a 94 km/h long shot from 25 m (about 1.1 s) allows only ≈0.3 m of steps. So he saves low corners about half the time but not full-stretch top corners. Measured on the QA D-3 grid (3 spots × x ±3.0/±3.3 × y 0.3/2.1, push 0.5, perfect timing): 16 goals / 5 saved / 3 caught of 24. Central long shots (x −1.5/0/1.5, y 0.5/1.2): 2 goals of 18, with 10 saved and 6 blocked by the defender.
- **Penalty read:** the cue is the side the kick is aimed at: the no-scatter preview crossing, with |x| < 0.5 m counted as "centre". The keeper follows the cue with probability 0.65, otherwise he picks the other side (for a central cue, left or right 50/50). `disguise` inverts the cue (a central disguise reads as right). Before his reaction time the keeper only pre-shifts gently towards his guess (8 m/s², ≤ 1.8 m/s), so a central mid-height shot remains saveable. With the pre-shift at 10 m/s² / 2.2 m/s, 25 % of central shots went in, which failed the ≤ 20 % target.
- **Keeper plan draws:** reaction is uniform in 0.20–0.25 s (seeded). Every strike draws exactly two Gaussians (scatter), one reaction value and one guess value from the sim RNG, so a replay with the same seed and intents is bit-identical.
- **Scatter:** σ = 0 below 90 % power, 1.5° at exactly 90 %, rising to 3.5° at 100 %. It is applied independently to azimuth and elevation. Timing σ combines with it in quadrature. `kick.scatterDeg` reports that combined σ, not the drawn deviation.
- **Timing scales ball speed:** speed = (40 + 75·power)·mult. Penalty run-up: ×1 within ±80 ms, then linear to ×0.75 at 400 ms. Long shot ("early/late costs 10–25 %"): ×0.90 just outside ±80 ms, linear to ×0.75 at 400 ms. The extra σ reaches 3° at 400 ms in both. (Fix round: this used to scale power.)
- **Strikes are accepted only in free kick `aiming`, penalty `runUp` and long shot `pushed`.** A penalty strike without a run-up and a long-shot strike before the push are ignored. `cancelRunUp()` returns a penalty run-up to `aiming` with the taker back beside the ball and no penalty. A run-up still pending 1.0 s after its ideal contact is aborted the same way.
- **Long shot push is a short touch:** speed 2.2 + 1.3·power m/s, with rolling top spin v/(2πr). The taker finishes the touch (0.3 s) and then chases at ≤ 7.5 m/s. The ideal contact comes when he reaches his strike position beside the ball: it is computed at the push by running the same deterministic roll and chase forward, and announced in `runUpStart.contactAt` (`startRunUp()` returns it). Measured roll at the ideal contact: 1.98 m (power 0), 3.07 m (0.5), 4.35 m (1), at 1.09/1.31/1.52 s. If there is no strike by contact + 0.6 s, the taker scuffs it: aimed at the goal centre azimuth, elevation 0.08, power 0.2, maximum timing penalty. It is still ≥ 20 m out from every ls-* spot.
- **Closing defender (QA D-3 fix):** he starts 12 m in front of the ball on the ball→goal-centre line and reacts 0.3 s after the push. He closes at ≤ 6 m/s, holds at least 3.5 m from the ball (matching its approach) and freezes at the strike. He is a standing capsule with arms down: radius 0.25, height 1.8. At a perfectly timed strike he is 7.5 m / 5.9 m / 4.2 m away for push power 0 / 0.5 / 1. He blocks low and central shots through his body cone but not well-placed corners. Before the fix he was 2.4 m away, 1 m off the line, and blocked the whole half of the goal on his side at every height.
- **Target aim with a moving ball:** the RESULTING launch (kick + full ball velocity, sideways component included) is solved to reach the target. Its speed is iterated so that |resultant − ball velocity| equals the kick speed, which matches the swipe (angles) path where the ball velocity is added vectorially. Dial targets below y = 0.11 are clamped to 0.11 before solving, so aim stays continuous at the bottom of the goal.
- **Solver fallback (unreachable target):** aim straight at the target's azimuth, with elevation equal to the line-of-sight angle plus half the vacuum 45° loft term, clamped to −0.1…0.8 rad.
- **Result rules:** a goal is decided the moment the ball centre passes z < −0.11 inside the posts and under the bar. It still counts after touching the frame or the keeper, and no net contact is used. Otherwise the ball is decided when it is caught, crosses the line outside, stops, leaves the area, or has been heading upfield for 0.5 s after any block contact, or at 6 s. Priority: caught > saved > post/bar (first frame touch) > wall/defender > miss.
- **Summary stats:** `apexM` and `lateralCurveM` cover the free flight only (until the first non-ground contact or the line crossing). `missDistanceM`: 0 for goals. For shots touched by the keeper, wall, defender or frame before any line crossing, it is measured from the free-flight predicted crossing: a `simulate` of the same launch with the same seed, identical to the live flight up to the contact; 0 when that was on target. Otherwise it uses the real crossing, else the closest approach. `timeToGoalS` is the keeper's first touch for saved/caught, the first wall/defender touch for `wall`, otherwise the crossing time, else the first contact or the decision time.
- **A long shot blocked by the closing defender reports `ShotResult` 'wall'.** The contract has no 'blocked'; the contact tag is 'defender' and the UI labels it by mode.
- **Event hygiene:** ground contacts are emitted only for bounces (vertical speed > 1 m/s). Same-tag contact events are merged within 0.15 s, so a net or rolling ball does not flood the listeners. `save` is emitted on the first keeper touch, and again as `caught: true` if a later slow touch holds it.
- **Recording:** a `Recording` object is assigned to `state.lastRecording` at the result. Its `frames`/`events` arrays keep growing for the 0.5 s tail, so the UI can start the replay immediately. After the tail the sim keeps stepping the ball physics (ball settles in the net) until `resetShot`.
- **`update(dt)` clamps a frame to 0.1 s.** The sim clock advances in exact 1/240 s steps.
- **Taker:** stands 0.6 m left of and 0.5 m behind the ball relative to the ball→goal-centre direction (mirrored for left-footers). The penalty run-up starts 1.3 m left and 2.2 m back (≈2.55 m) with a smoothstep over 0.9 s.
- **Session log best kick:** goals beat non-goals. Among goals, the smallest distance from the crossing to any of the four inner corners of the mouth wins; among non-goals, the smallest miss. Stored paths are rounded to mm. Invalid entries in storage are dropped individually.

### ui

- **Finger speed is measured over the last 80 ms before release,** not over the whole swipe. A flick is judged by its release speed; a slow wind-up followed by a fast flick is a fast kick. A lift-off with no movement is ignored so it does not dilute the speed.
- **CSS px → metres: 96 CSS px per inch for fine pointers (mouse), 150 CSS px per inch on coarse pointers (`(pointer: coarse)`, touch tablets/phones lay out ≈132–160 CSS px per physical inch).** Fix round: with 96 on tablets a physical flick read ~1.5× too fast. Chosen once per scheme attach.
- **Power ease-in exponent 1.6** (power = f^1.6, f = normalised finger speed 0.3–2.5 m/s). Mid-speed swipes give ~33 % power, so full power needs a real flick.
- **Swipe curvature = signed area between the path and its chord / chord².** Dead zone 0.01; full ±10 rev/s at 0.12 (a circular arc whose sagitta is ~18 % of the chord). The ball curves the way the swipe hooks: a swipe that bows left of its chord (hooks right at the end) gives sideSpin > 0 (curves to +x).
- **Swipe azimuth = the chord direction, read on the pitch.** The screen images of 1 m towards the goal centre and 1 m to the right at the ball (via `worldToScreen`) turn the screen direction into a ground direction; straight up the screen always aims at the goal centre. Swipes more than 80° off that direction, backwards swipes and swipes shorter than 24 px give no kick.
- **Start on the ball → elevation 2° (top) / 11° (centre) / 20° (bottom), top spin up to +5 and back spin up to −5 rev/s.** The top…bottom band is ±max(40 CSS px, 2.2 r) around the ball centre with a ±10 px centre dead band (fix round: a 10–20 px ball is too small to hit its top or bottom exactly). 20° is enough to clear a wall from ~20 m.
- **A swipe must start within max(4 ball radii, 120 px) of the ball centre.** "On or near the ball" while still letting a thumb start slightly below it.
- **`createSwipeScheme({ ballWorld })` takes an optional ball-position provider.** `InputContext` only exposes the ball's screen position, which is not enough to project a ground direction; without the option the scheme falls back to screen-up = goal, screen-right = right.
- **Dial power bar: hold = triangle wave 0→1→0 over 1.6 s, release sets it; a tap (<180 ms, no drag) sets the tapped value exactly.** The tap and the ±1 % arrow keys make the dial repeatable, as the brief requires "everything numeric and repeatable".
- **Knobs step 0.5 rev/s; drag up/right increases (10 px per rev/s for curve, 16 px for dip); arrow keys ±0.5, Home/0 or double-click resets.**
- **Reticle range x ±12 m, height 0–6 m on the goal plane,** so a mis-aim well wide/over is possible. Pressing anywhere on the empty play area moves the reticle there.
- **Gesture plan per mode/phase (`gesturePlan`):** free kick = strike; penalty = the press starts the run-up, the release strikes; long shot = first gesture is a push, the second gesture's press starts the run-up (the app ignores the call if the sim already started one) and its release strikes. Nothing is accepted in flight/result/replay. The release re-checks the mode captured at press and that the current phase still allows that gesture kind (`releaseAllowed`), otherwise nothing is emitted.
- **A run-up the UI started is cancelled (`sim.cancelRunUp()`) when the gesture ends without a strike** (tap, too short/backwards swipe, pointercancel, Shoot cancelled, scheme detached). The long-shot run after a push belongs to the sim and is never cancelled by the UI.
- **Long shot, ball rolling ('pushed'): a tap on/near the ball is a strike** towards the goal centre along the pitch, 11° elevation, no spin, power = the dial's current power (default 0.7).
- **Menu, mode tabs, spot buttons, the disguise toggle and the mini-map ignore presses while a kick gesture is in progress** (`core.ui.gesture`, set by the schemes through an app-side context hook).
- **The penalty "disguise" toggle lives in the HUD and the app adds `disguise: true` to penalty strikes** instead of every scheme knowing about it.
- **The UI keeps its own list of spot keys/labels (`ui/spots.ts`)** because `data/presets.ts` did not exist when the UI was written; positions stay the sim's business (the mini-map shows `sim.state.ballStart`). Free placement is rounded to the metre and clamped to 16–35 m and ≥ 2 m in front of the line.
- **Screens are mounted/unmounted, not hidden,** so every `data-testid` (e.g. `btn-back`) exists once in the DOM at a time.
- **HUD layout mirrors with the kicking foot.** Right-footer: Talilei bottom-left, dial controls bottom-right, set-up panel top-left, shot card top-right. Left-footer: Talilei bottom-right, dial controls bottom-left, shot card top-left (the set-up panel moves top-right on medium/compact screens).
- **Three layout sizes.** Large (≥ 1100 × 700): dial controls in a row. Medium (< 1100 wide or < 700 tall, e.g. 1024×600): dial controls stacked in a 256 px column at the side so they stay clear of the ball, set-up panel horizontal (mini-map beside the spot buttons), and the dial column is hidden while the result card is shown (the card takes its place). Compact (< 900 wide or < 440 tall, e.g. 740×360, 800×500): smaller chrome, hint on one line with ellipsis, notes and last-input line hidden, 64 px Shoot. E2E checks Talilei's corner, the ball, panel overlaps, off-screen and ≥ 44 px targets at 740×360, 800×500, 1024×600, 1280×800 and 1920×1200 (both feet where the brief asks).
- **The shot card is a flex column with a scrolling data list (max-height = viewport − its top offset); the result line and the Next/Replay buttons are always visible.**
- **Edges are padded with `env(safe-area-inset-*)` (viewport-fit=cover).**
- **Title: three grid columns — logo | menu (clamp 280–420 px) | Talilei at full viewport height with his natural width** — so he can never cover the menu at any landscape width ≥ 740 px.
- **Stats/settings/title use the 3D title camera as a dimmed backdrop; the sim only advances on the play screen,** so run-up timing (sim clock) never runs in the background.
- **Replay shows the result, speed/spin, a side-view profile of the recorded path and a progress bar at 0.35×; it holds the last frame and offers "Replay again".** Its ghost is the best kick at the spot from before the replayed shot was recorded (never the shot itself).
- **`audio.unlock()` is called on every pointerdown/pointerup/touchend/click/keydown (it is idempotent and resumes a suspended context).** Fullscreen + landscape lock is attempted once, on the first trusted activation (pointerup/touchend/click/keydown) on a coarse-pointer device, never under automation (`navigator.webdriver`). Portrait shows the rotate prompt (pure CSS media query).
- **Without WebGL a pinhole fallback camera (2.3 m high, 4.5 m behind the ball, 46° FOV, 12° down) provides `worldToScreen`/`screenToGoalPlane`,** so both schemes and the E2E tests work with `scene === null`; the aim preview is then drawn in the SVG overlay.
- **The ball's screen position is exposed as `data-ball-x/y/r` on the input layer** so E2E (and QA) can aim swipes without reaching into the renderer.
- **"Inside/outside of the foot" labels:** right-footer: sideSpin < 0 (curls left) = inside; left-footer mirrored. Physics sign unchanged. Shown on the dial knob, in the last-input line (swipe too) and on the shot card (from the kick's launch side spin).
- **Shot card wording: result `'wall'` in a long shot reads "Blocked by the defender"** (QA D-2; the contract's `ShotResult` has no defender value and long shots have no wall).
- **Aim preview is throttled and cached:** at most one `sim.previewPath` per frame and at most one per 100 ms (≤ 10 Hz), with a 48-entry LRU cache keyed by the quantised aim (1 cm / 0.03°), power (0.5 %), spins (0.05 rev/s), kind, mode, spot, ball position, altitude and foot (fix round: a preview costs 10–19 ms on a tablet).
- **Mini-map snaps to the nearest whole-metre cell that is itself legal (16–35 m, ≥ 2 m out, on the map)** instead of rounding, so a rounded spot can never fall just inside 16 m or beyond 35 m.
- **Dial power bar: a cancelled press restores the power set before it.**
- **The run-up timing mirror (power/scatter formulas) was removed from `input/runUp.ts`;** the rule lives only in the sim. The UI keeps the ±80 ms window for drawing the zone and grading a release.
- **Brand lint:** `tests/unit/ui.brand.test.ts` fails on any hex, rgb/hsl/lab/color() or CSS named colour in `styles.css` other than #3FC9FC, #000E29, #FFFFFF and rgba() of them, and on any colour literal in `src/ui`/`src/input` TypeScript. The danger button is white-on-navy (no red).
- **E2E touch swipes use CDP `Input.dispatchTouchEvent` with explicit timestamps** for the power assertion, so the measured finger speed does not depend on CDP latency on a loaded CI machine.
- **HUD state is synced once at mount and on tab/spot clicks, not only in the animation loop,** so the HUD is complete even when frames are slow (headless SwiftShader measured ~2.7 fps at 1280×800 and <0.5 fps on the DPR-2.25 tablet profile).
- **Input E2E tests wait for the ball's projected position to be stable and on screen before swiping, and use `test.slow()`.** The kick camera is only placed by `scene.render`, so projections are off-screen for the first frames after entering a mode; at sub-1 fps every CDP touch event also waits for a frame.

### release

- **Service worker generated by an own Vite plugin (`scripts/sw-plugin.ts`) instead of vite-plugin-pwa or `scripts/build-sw.mjs`.** No new dependency; running inside `vite build` (`closeBundle`, post) means every build — `npm run build`, the E2E `webServer` build, `--outDir` variants — gets a matching worker with no extra step. The static `public/sw.js` placeholder was deleted so it can never overwrite the generated one. (ARCHITECTURE.md §3 still names `scripts/build-sw.mjs`; it should say `scripts/sw-plugin.ts`.)
- **Precache list = every file in the output folder after the build, minus `sw.js` and `*.map`.** Walking the folder (rather than Rollup's bundle) includes the copied `public/` files (manifest, icons) with no allow-list to keep in sync.
- **Cache version = first 12 hex chars of SHA-256 over file names and contents.** Any changed byte produces a new `sw.js`, which is what makes the browser install an update; unchanged builds keep the same worker.
- **All worker URLs are resolved relative to the worker's own URL.** Works under `/<repo>/` on GitHub Pages and from any folder, matching Vite `base: './'`.
- **Navigations are served cache-first from the cached `index.html` (app shell).** The cached shell always references the hashed files in the same cache, so a page is never a mix of two versions; a network-first shell would break offline start on flaky tablet Wi-Fi.
- **No `skipWaiting()` and no update message handler (fix round: the unused `'skipWaiting'` handler was removed).** A new version installs in the background and applies only after every app window/tab is closed and the app is reopened; the README says exactly that. Taking over a running game could leave the page requesting hashed files the new cache no longer has. `clients.claim()` on activate makes the very first visit controlled, so it is offline-ready without a reload.
- **Non-precached or cross-origin requests are not intercepted.** The game has no runtime network data; letting them go to the network keeps the worker simple and avoids caching anything unbounded.
- **Manifest gains `id: "./"`, `lang`, `dir` and `categories`.** A stable `id` keeps the installed app's identity if `start_url` ever changes; the rest are metadata stores and launchers read. Other fields were already right.
- **`static-check` also enforces the 6 MB download budget** (sum of all files in the build, worker included, 1 MB = 10⁶ bytes) and prints the five largest files, so the budget is checked every time the static check runs.
- **`static-check` is strict by default (requires `[data-testid="btn-mode-freeKick"]`) with an `--allow-stub-ui` escape for early phases.** The Phase 3 run must prove the real title screen appears; the flag only exists so the script could be verified before the UI landed.
- **Offline E2E runs twice: at the `vite preview` root and under `/LT26/` served by a tiny Node static server inside the spec** (from `PW_OUT`, the folder the webServer just built), so it needs no Python and no second webServer entry. It requires the title button online (count > 0) and offline, and `scene.getStats().drawCalls > 0` offline, so it cannot pass against an empty page.
- **Offline E2E asserts `response.fromServiceWorker()` only on Chromium.** Playwright reports that flag only for Chromium; on WebKit/Firefox a clean offline boot with zero failed requests is the proof.
- **`vite.config.ts` imports the plugin as `./scripts/sw-plugin.js`.** Vite warns that extensionless imports are unsupported by its future native config loader; `.ts` would need `allowImportingTsExtensions` in tsconfig, which I may not edit. TypeScript's Bundler resolution maps `.js` to the `.ts` source.
- **Pages workflow uses separate build and deploy jobs, Node 22, `actions/configure-pages@v5`, `upload-pages-artifact@v3`, `deploy-pages@v4`, concurrency group `pages` without cancel-in-progress.** This is GitHub's reference layout; not cancelling avoids half-finished deployments. It builds with `npm run build` (type-check included) and does not rerun tests — CI does that on the same push.
- **CHANGELOG lives at the repository root** (my brief), not `docs/CHANGELOG.md` as in the brief's §5 tree; the root is where people and tooling look for it.
- **README states iPadOS/iOS 16+ as the Safari floor.** It is the oldest Safari with the WebGL 2 and service-worker behaviour the game relies on that is still commonly in use; the brief only says "Safari on iPad/iPhone".
- **CI split (fix round): a fast `check` job (lint, unit, build, `static-check`, 20 min) and an `e2e` matrix with one job per Playwright project (60 min each, `fail-fast: false`), each installing only its browser.** Parallel jobs keep wall time near the slowest project; `fail-fast: false` shows every browser's result. Superseded runs on the same ref are cancelled.
- **WebKit, iPad and Firefox jobs pass `--grep-invert visual\.spec\.ts`.** The visual tests are not tagged `@visual`, but Playwright's grep matches against the title path including the file name, so this excludes exactly visual.spec.ts (verified with `--list`). Baselines exist only for chromium and tablet-android on Linux.
- **Pages workflow runs `npm run lint` and `npm test` before the build** so a red tree never deploys, without repeating the slow E2E suite (CI covers that on the same push).

### qa

- **Integration tests fly the ball on the sim clock after the real gesture.** The swipe / dial / mouse gesture is real (CDP touch events, mouse), but once the `kick` event is seen the test advances `__lt26.sim.update(0.1)` from `page.evaluate` until `result`. Headless SwiftShader runs at a few fps (below 1 fps on the tablet profile) and the frame loop clamps dt to 0.1 s, so waiting on rAF would cost minutes per kick; the fixed 240 Hz sub-stepping makes the outcome independent of how the time is batched.
- **Penalty / long-shot strikes are released just before the ideal contact.** After the press (run-up) or the push, the test advances the sim to 60–100 ms before `runUpStart.contactAt` and then swipes; the exact timing error is whatever the page measured and is shown on the card, not asserted.
- **Long-shot card speed bound is 115 + 21.6 km/h.** The brief (§1.1) says the moving ball's velocity adds to the kick; the push is at most 6 m/s (21.6 km/h), so a long-shot strike can legitimately exceed the 115 km/h power ceiling. All other modes are checked against 40–115 km/h (with 1e-6 tolerance for float rounding at exactly 40).
- **"Frames match" means 60 Hz from strike to result + 0.5 s.** `lastRecording.frames.length` must equal `floor((t_result − t_kick + 0.5)·60) + 1` within ±2, and every world the scene renders on the replay screen must be one of the recorded frames (proves playback, not re-simulation). The trail check wraps `scene.setTrail` and requires a call with exactly `lastShot.path.length` points.
- **Distribution tests run on the title screen.** The app's frame loop only advances the sim on the play screen, so on the title screen the test owns the sim clock completely; kicks go through `sim.applyIntent` / `startRunUp` exactly as the UI would call them, with `atMs = sim.state.time·1000`. Seeds are not fixed (the app seeds from `Date.now()`), so each run is a fresh sample.
- **Penalty inputs:** "low corner" = dial target x = ±2.9…3.2 m, y = 0.25…0.35 m, power 0.85, timing within ±70 ms, 1 in 5 with disguise; "central mid-height" = x within ±0.3 m, y 1.0–1.4 m, power 0.55–0.85.
- **Free-kick "repeatable curling goal"** = the aim-assist (`sim.solveAim`) launch for a candidate (target near a corner, 75–105 km/h, |side spin| 6–9 rev/s, top spin 0/2) scores with a lateral curve > 0.5 m, and the same kick then scores in at least 2 of 3 repeats (fresh keeper reaction and noise each time). The grid includes 75 km/h and x = ±3.3 m: a first grid without them (85–105 km/h, x = ±3.0/2.6) found nothing from the D edges, which an exhaustive 2,000-kick exploration showed was a search-grid limit, not a product defect.
- **Long-shot timing check compares launch speeds of the same intent at 0 ms and ±250 ms** (≥ 5 km/h lower when late/early), using the `kick` event's launch speed.
- **Perf test renders 100 aiming frames + 200 frames with a curling kick in flight** by calling `scene.render(sim.state.world, 1/60)` in one `page.evaluate`, and gates on the maximum draw calls / triangles over all 300 frames (not the mean). Mean render time is measured around each call and printed but not gated.
- **Visual baselines mask the canvas only where it animates by itself** (title orbit camera, replay orbit camera, post-result ball roll, replay progress bar). Play screens compare the full 3D kick view. The shot-card test freezes `Date.now()` before boot so the sim seed, the keeper and the card numbers are deterministic. Screenshot timeout is 60 s (a stable SwiftShader screenshot at 1280×800 takes > 10 s). Baselines exist per project (chromium and tablet-android), both at a 1280×800 viewport.
- **Unmasked review copies** (`review-*.png`) are written to the test output folder for people to look at; they are not compared.
- **Replay-frame check polls for 3 distinct rendered frames (up to 90 s)** instead of a fixed 3 s wait: on the tablet profile SwiftShader rendered no frame at all in 3 s, which failed the test without any product fault.
- **Defect-documenting tests live in `qa.defects.spec.ts`** and are expected to fail until the defect is fixed (none are skipped).
- **Round 2: the sim clock is held during a CDP gesture that must land at a chosen time.** `freezeSimClock` no-ops `sim.update` (the frame loop keeps rendering) while the penalty / long-shot strike swipe is dispatched, after `runToContactAndFreeze` has run the sim to 20 ms before the ideal contact. Without it each headless CDP event costs up to 0.1 s of sim time and the new run-up abort (contact + 1 s) and long-shot auto-scuff (contact + 0.6 s) fire before the release.
- **Round 2: long-shot "well-placed" kicks aim at the far corner from the closing defender with the longest push.** The shorter push (intentional change) leaves the defender in the line of every near-side shot; that is filed as D-3 with its own failing test rather than hidden by the distribution test.
- **Round 2: animated canvases are hidden, not masked, in the visual baselines.** A `mask` box is painted over the whole page for a full-screen canvas (round-1 baselines were blank). The canvas gets `display: none` and `scene.render` is paused for the screenshot (a hidden SwiftShader canvas otherwise stalls the capture for minutes), then both are restored. All baselines are deleted before regenerating, because `--update-snapshots` keeps a baseline that is within tolerance.
